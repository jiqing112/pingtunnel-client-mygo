## 2. 观测结果

### 2.1 OS 层 ping

```
ping -n 3 <SERVER_IP>      → 3/3，136ms，TTL 128
ping -n 3 -l 1000 ...          → 3/3，137ms
ping -n 2 -l 1400 ...          → 2/2，137ms
```

TTL 128 与"Linux 服务器默认 64"不符（137ms 跨境通常剩 40–60），提示应答者可能是链路上的 NAT/边缘设备。

### 2.2 裸 ICMP 探针（`pingtunnel-workbench/wire_diag_test.go`，`-tags diag`）

用 `golang.org/x/net/icmp` 手工构造 ICMP echo，载荷是 pingtunnel 的 `MyMsg{PING}`：

| 用例 | 结果 |
| --- | --- |
| magic 正确（`0xDEAD`）、key `<KEY>` | 回包 `icmpType=0 id=1234 seq=n rproto=0 type=1 key=<KEY> magic=57005`，约 137ms |
| **magic 故意改成 `12345`** | **依然原样回弹**，约 137–143ms，5/5 |

第二行是判据：pingtunnel 在处理前会校验 `MyMsg_MAGIC`，magic 错必丢。**所以这些回包不是 pingtunnel 写的**，是主机内核/边缘设备对 ICMP echo 的正常应答（把我们的载荷原样带回）。

复现：

```powershell
. .\dev.ps1
cd pingtunnel-workbench
$env:PT_SERVER='<SERVER_IP>'; $env:PT_KEY='<KEY>'
go test -tags diag -run TestWire -v .
```

### 2.4 数据通路（socks5 实测）

隧道跑着（本地 `34455` LISTENING），用 curl 走 socks5 分别试三个目标：

curl --socks5-hostname 127.0.0.1:34455 -m 15 https://www.baidu.com
curl --socks5-hostname 127.0.0.1:34455 -m 20 https://x.com

| 目标 | 结果 |
| --- | --- |
| `https://www.baidu.com` | `code=000`，15s 超时 |
| `https://x.com` | `code=000`，20s 超时 |

所以：**这不是“某个网站不通”，是隧道单向——发出去的数据没有一个字节回来**。Twitter 只是最先被注意到的那个。

## 3. 两种假设，以及怎么区分

| | 假设 A：服务端没收到/没应答 | 假设 B：服务端正常，回程被限速 |
| --- | --- | --- |
| 现象 | 短突发能通、持续流量没响应 | 突发和持续都应有响应，只是丢一部分 |
| 与观测是否一致 | 一致（5/5 突发全回，但持续多分钟时才偶发） | 部分一致，需要看到 `rproto=-1` 的包 |
| 判别方法 | 服务端 `tcpdump` 看不到我们的 echo request | 服务端看得到请求，也能看到自己的回包 |

当前证据更偏向 **A 或"半 A"**（边缘代答、虚拟机收不到原始 ICMP 载荷），但**没有服务端抓包，不能定论**。

### 4.0 系统上没有 tcpdump（最小化镜像）

三选一，均无需 sudo（当前已是 root）：

**办法一：前台跑服务端看日志（最直接，不用装任何东西）**

```bash
systemctl stop pingtunnel
/bin/pingtunnel -type server -key <KEY> -loglevel debug
# 这期间让客户端连（本机点「启动隧道」），看到 ping from <客户端 IP> 就是收到了
# Ctrl+C 后：systemctl start pingtunnel
```

**办法二：看内核 ICMP 计数（不停服务、不装东西）**

```bash
counters() { awk '/^Icmp:/{if(++n==1){for(i=2;i<=NF;i++)h[i]=$i}else{for(i=2;i<=NF;i++)printf "%s=%s ",h[i],$i;print ""}}' /proc/net/snmp; }
counters; sleep 30; counters
```

这 30 秒内让客户端连。先拿一台能通的电脑校准（InEchos 会涨），再拿这台对比。
判读：`InEchos` 涨 ≈ 请求到了 VM；不动 ⇒ 请求根本没进来（安全组 / 运营商 / NAT）。
注意 `OutEchoReps` 只能说明内核回了 ping，**不能**证明 pingtunnel 回了包。

**办法三：装 tcpdump**

```bash
apt-get update && apt-get install -y tcpdump     # Debian / Ubuntu
# 或 yum install -y tcpdump / apk add tcpdump
tcpdump -ni any icmp and host <CLIENT_IP>
```

## 4. 服务端五分钟能做完的检查

按顺序，任一条即可定性：

1. **确认公网 IP**
   ```bash
   curl -s ifconfig.me
   ```
   ≠ `<SERVER_IP>` ⇒ 服务器在 NAT 后，ICMP 到不了它，问题在映射/安全组。

2. **抓包看有没有进 VM**
   ```bash
   sudo tcpdump -ni any icmp
   ```
   同时在本机点「启动隧道」：
   - 看不到来自本机公网 IP 的 `echo request` ⇒ 包没进虚拟机（NAT/安全组/云端 ICMP 过滤）。
   - 看得到请求、看不到 `echo reply` ⇒ 服务端没应答，继续第 3 步。

3. **前台跑服务端，看日志**
   ```bash
   sudo systemctl stop pingtunnel
   sudo /bin/pingtunnel -type server -key <KEY> -loglevel debug
   ```
   （不要加 `-noprint`，否则看不到日志）
   - 打印 `ping from <IP> ...` ⇒ 服务端收到了，应答路径有问题。
   - 什么都不打印 ⇒ 服务端收不到，回到第 2 步。

4. **安全组/防火墙**
   确认放行的是 ICMP（尤其是"自定义 ICMP"而不是仅 TCP/UDP），并注意云厂商对 ICMP 的**速率限制**：短突发能过、持续流量被限，正是本文 2.2 与 2.3 的差异形态。

## 6. 结论边界

能确定的：**客户端发得出、本机能收到 ICMP 回显；持续 ICMP 往返不稳定，且现有"回包"多数不是 pingtunnel 写的。**

不能确定的：服务端是否收到过我们的请求、是否应答过。这需要第 4 节的抓包/日志，本机无法替代。

因此当前不建议上 TUN 全局代理：链路是否成立尚未确认，全局接管只会把"某站打不开"放大成"整机卡顿"，并让两个未知量（实现错误 / 链路不通）相互掩盖。

## 8. 根因（2026-10-22 00:12 实测定案）

结论先说：**不是版本问题，也不是 server 坏了**。是这台客户端所在的 NAT「同一请求只放行一个 ICMP 回包」，而服务器上有两个东西会回包。

### 8.1 现场

用 SSH 登进服务器，把服务端停掉、前台带 debug 跑一次：

```bash
systemctl stop pingtunnel
/bin/pingtunnel -type server -key <KEY> -loglevel debug > /tmp/pt.log 2>&1 &
```

本机随便发几个 pingtunnel PING，服务器日志立刻出现：

```
[INFO] [server.go:140] [main.(*Server).processPacket] ping from <CLIENT_IP> ... 0 4012 13774
[DEBUG] [server.go:233] [main.(*Server).processDataPacket] processPacket bed1aa... <CLIENT_IP> 16
...
sendpong 1 / recvpong 1 / rtt 138.214434ms
```

⇒ **请求到了，服务端也回了 pong**。但本机这边一个都没收到。

### 8.2 为什么会收不到

同一个请求会引出**两个 (id, seq) 完全相同**的 ICMP echo reply：

| 来源 | 载荷 | 本机是否收到 |
| --- | --- | --- |
| 服务器内核（对 echo request 的自动应答） | 原样字节，`rproto=0` | ✅ 收到 |
| pingtunnel 服务端（`sendICMP` 显式发的回复） | 改过 1 字节，`rproto=-1` | ❌ 被丢 |

这台机器是 VMware 虚拟机（网关 MAC `00:50:56:E8:D7:15`），走的是 VMware 的 NAT。它的 ICMP ALG 把回包按 (id, seq) 做状态匹配，**同一请求只转发第一个回包**；内核那条先到，pingtunnel 那条被判成"重复"丢掉。

这也解释了「别的电脑能连」：它们不在这种严格 NAT 后面，两个回包都收到，客户端按 `rproto=-1` 取正确那个。

### 8.3 验证

在服务器上临时关掉内核 echo，让"每请求两个回包"变成"只有一个"：

```bash
sysctl -w net.ipv4.icmp_echo_ignore_all=1
```

立刻见效：

```
← from <SERVER_IP> type=0 id=1234 seq=3 len=37 rproto=-1 (rtt 138ms)
```

（`len 37` 就是服务端那条，`rproto=-1`。）随后真实链路：

```
curl --socks5-hostname 127.0.0.1:34555 http://www.baidu.com
→ code=200 time=3.529s
```

GUI 客户端同样通过：`code=200 time=7.570s`，界面 RTT 136ms、每秒一个 pong。

## 9. 修复

服务器上已落盘：

```bash
/etc/sysctl.d/99-pingtunnel.conf
    net.ipv4.icmp_echo_ignore_all = 1
```

代价：**这台服务器不再响应 ping**（`icmp_echo_ignore_all` 是全局开关）。对一台专职跑隧道、又必须从严格 NAT 后面访问的机器，这笔交换是值得的；如果你依赖 ping 做存活监控，改用 TCP 端口探测即可。

回滚：

```bash
rm /etc/sysctl.d/99-pingtunnel.conf && sysctl --system
```

另一条不改服务器的路：**把客户端虚拟机的网络从 NAT 改成桥接**，让它别经过 VMware 的 ICMP ALG。那样服务器可以继续响应 ping。

### 9.1 顺带发现的第二个问题

服务端在 22:11 和 22:39 各崩过一次，都是：

```
panic: runtime error: invalid memory address or nil pointer dereference
main.(*Server).processDataPacket  server.go:266
```

systemd 的 `Restart=always` 把它拉了起来。这两天恰是客户端往隧道里灌 DATA 的时刻，所以很可能是这条老分支在某个 DATA 分支上的空指针。修好回包后本轮没再复现；如果它频繁出现，把服务端换成上游新版（协议兼容）即可绕开。

## 10. 复盘：为什么前面几轮判断错了

- “TTL 128 说明不是 Linux 服务器” —— 不成立，本机对照 `8.8.8.8` 也是 128，TTL 被本地链路规范化过。
- “magic 改错也被回弹 ⇒ 回包不是 pingtunnel 写的” —— 结论正确，但**不能**推出“服务器没收到”；它只说明**收到的那个包**不是 pingtunnel 的。
- “上行 34KB / 下行 0KB” —— 这是最有力的数据，指向“单向”，但当时无法区分是服务端不回还是回程丢包；直到登进服务器看见 `sendpong 1` 才定案。

## 11. 另一个产品级问题：残留子进程占着端口

现象（用户截图）：启动即 `出错了 / 客户端已退出`，日志里是

```
Error listening for tcp packets: listen tcp :34455: bind:
Only one usage of each socket address (protocol/network address/port) is normally permitted.
```

原因：应用被强杀（或上次异常退出）时，`pingtunnel.exe` 子进程成了孤儿，继续监听 `34455`；下次启动自然抢不到端口。

处置（已实现）：

- 启动前先查端口占用者；若占用者**就是本程序会启动的那个 `pingtunnel.exe` 路径**，直接结束它并继续（日志写「已清理上次残留的客户端进程（PID x）」）；
- 若占用者是别的程序，横幅给出 PID + 进程名 + 两条出路（结束它 / 换端口）；
- 子进程意外退出时，横幅改为显示它最后那行错误，而不是 `exit status 2`。
